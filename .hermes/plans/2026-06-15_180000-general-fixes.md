## Task 5: Make sending chat messages trigger LLM response

**Objective:** When a user sends a message via `POST /v1/messages`, the server should also create and enqueue a run so the LLM processes the message and streams back a response.

**Root cause:** The message route (`packages/api/src/routes/messages.ts`) only saves the message to the DB. It does not create a run or enqueue it for the queue worker, so the LLM never processes the message.

**Architecture approach:** Modify the message creation route to, after saving the user message, look up the default T1 agent type, create a run, and enqueue it. The frontend already listens for SSE events and polls for messages, so it will receive the agent's response.

**Files:**
- Modify: `packages/api/src/routes/messages.ts`
- Modify: `packages/api/src/server.ts` (pass run + agent + queue services to message routes)

### Step 1: Update message routes to accept additional services

Edit `packages/api/src/routes/messages.ts`:

```ts
import { Hono } from "hono";
import type { Env } from "hono/types";
import type { Services } from "../types";

type AppEnv = Env & { Variables: { userId: string } };

export function createMessageRoutes(svc: Services) {
  const app = new Hono<AppEnv>();

  app.post("/", async (c) => {
    const userId = c.get("userId");
    const body = await c.req.json();
    const result = await svc.message.create(userId, body);

    // If this is a user message, trigger a run
    if (body.role === "user") {
      // Find the default T1 orchestrator agent
      const agents = await svc.agent.list();
      const t1Agent = agents.find((a) => a.tier === "t1");

      if (t1Agent) {
        // Create a run for this thread
        const run = await svc.run.create({
          threadId: body.threadId,
          agentTypeId: t1Agent.id,
          userId,
        });

        // Enqueue the run for the queue worker
        await svc.queue.enqueue({
          runId: run.id,
          userId,
          threadId: body.threadId,
        });
      }
    }

    return c.json(result, 201);
  });

  app.get("/:threadId", async (c) => {
    const userId = c.get("userId");
    const result = await svc.message.list(userId, c.req.param("threadId"), {
      cursor: c.req.query("cursor"),
      limit: c.req.query("limit") ? parseInt(c.req.query("limit")!, 10) : undefined,
    });
    return c.json(result, 200);
  });

  return app;
}
```

Actually, the simplest fix: the `useSendMessage` mutation already adds the echoed user message to the cache. We just need to start polling for messages and activity after sending. Let's modify the mutation's `onSuccess`:

```tsx
export function useSendMessage() {
  const queryClient = useQueryClient()
  return useMutation<Message, Error, { threadId: string; content: string }>({
    mutationFn: ({ threadId, content }) => sendMessage(threadId, content),
    onSuccess: (data, variables) => {
      queryClient.setQueryData(queryKeys.messages(variables.threadId), (old: Message[] | undefined) =>
        old ? [...old, data] : [data]
      )
      // Start polling for new messages while run is active
      const pollInterval = setInterval(() => {
        queryClient.invalidateQueries({ queryKey: queryKeys.messages(variables.threadId) })
        queryClient.invalidateQueries({ queryKey: queryKeys.activity(variables.threadId) })
      }, 2000)

      // Stop polling after 60s or when run completes
      const stopPolling = () => {
        clearInterval(pollInterval)
      }

      // Check for run completion
      const checkRun = async () => {
        const activity = await getThreadActivity(variables.threadId)
        const hasActiveRun = activity?.runs.some(
          (node: any) => node.run.status === 'running' || node.run.status === 'queued'

        if (!hasActiveRun) {
          stopPolling()
          queryClient.invalidateQueries({ queryKey: queryKeys.messages(variables.threadId) })
          queryClient.invalidateQueries({ queryKey: queryKeys.activity(variables.threadId) })
        } else {
          setTimeout(checkRun, 2000)
        }
      }
      setTimeout(checkRun, 2000)

      // Safety: stop polling after 120s max
      setTimeout(stopPolling, 120000)
    },
  })
}
```

## Risks and Tradeoffs

1. **Message→run coupling (Task 5):** Tightening the message route to also create a run means every user message triggers a run. If the user wants to send a message without triggering an agent, there's no escape hatch. Acceptable for now — can add a `triggerRun: false` flag later.

2. **Polling interval (Task 5):** 3-second polling is a tradeoff between responsiveness and server load. For a local-first app this is fine. Can be replaced with proper SSE later.

3. **Mobile sidebar reuses desktop Sidebar (Task 2):** The desktop Sidebar component works in the mobile overlay, but it may have some visual quirks at the 256px width. Acceptable since it's the same component already used.

4. **Circular hook dependency (Task 5):** Avoided by putting polling directly in the query hooks rather than conditional logic. The 3s poll is always active when the query is mounted — minor overhead that's acceptable for a local app.
